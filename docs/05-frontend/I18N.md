# Internationalization (i18n)

> Bilingual UI and locale persistence for the HRM SPA.
>
> Settings business: [../02-business/settings/README.md](../02-business/settings/README.md)  
> API: [../06-api/AUTH_API.md](../06-api/AUTH_API.md) · [../06-api/SETTINGS_API.md](../06-api/SETTINGS_API.md)

---

## Supported locales

| Code | Language | Role |
|------|----------|------|
| `vi` | Vietnamese | **Default** |
| `en` | English | Secondary |

No other locales in v1. Do not invent codes (`vn`, `vi_VN`, etc.).

---

## Resolution order (effective locale)

```
user.locale  ??  company.locale  ??  config('app.locale')  →  vi
```

| Layer | Storage | Who updates |
|-------|---------|-------------|
| User preference | `users.locale` (nullable) | Any authenticated user via `PUT /api/me/locale` |
| Company default | `settings` `company.locale` | `can_manage_settings` via `PUT /api/settings` |
| App fallback | `APP_LOCALE` / `config('app.locale')` | Env / deploy |

- `users.locale = null` means “follow company”.
- Guests (login, forgot password) use bootstrap locale `vi` until `/api/me` hydrates after login.

## Frontend stack

| Item | Choice |
|------|--------|
| Library | `i18next` + `react-i18next` |
| Catalogs | `resources/js/locales/{vi,en}/*.json` |
| Init | `resources/js/lib/i18n/` |
| Source of truth for SPA locale | REST `/api/me` (`locale`, `user_locale`, `company_locale`) — **not** Inertia shared props |

Sync `document.documentElement.lang` when language changes.

## Catalog namespaces

| Namespace | Use |
|-----------|-----|
| `common` | Shared buttons, empty/error/loading, weekdays, confirmations |
| `nav` | Sidebar / shell labels |
| `auth` | Login, password, 2FA, passkeys |
| `employees` | Employee module |
| `organization` | Org hierarchy UI |
| `roles` | Roles & permissions UI (includes `system_roles.*` for seeded roles) |
| `permissions` | Localized permission name + description per `can_*` key |
| `settings` | Company / profile / security / appearance settings |
| `audit` | Audit logs UI + `actions.*` / `subjects.*` domain labels |
| `attendance` | Attendance + corrections |
| `leave` | Leave requests, types, holidays, weekend rules |
| `shifts` | Shifts, assignments, overtime, my-schedule |
| `payroll` | Payroll runs, compensation, payslips |
| `documents` | Company / employee documents |
| `assets` | Asset inventory, assign/return, maintenance |
| `recruitment` | Job openings, candidates, interviews, offers |
| `onboarding` | Onboarding cases, tasks, templates |
| `notifications` | Inbox + preferences |
| `reports` | Reports + exports |
| `performance` | Goals, review cycles, evaluations, promotions |
| `dashboard` | Dashboard KPIs |

Use keys as `t('namespace:key')` or `useTranslation('namespace')`.

Both `vi` and `en` catalogs **must** contain every key used. Missing keys on the default `vi` locale are a defect.

Domain status enums from the API stay English codes (`pending`, `draft`); **display** labels go through module `status.*` keys (or `common:status_*` for employee lifecycle).

### Permission catalog parity

`permissions` namespace keys **must** match every key in `App\Support\PermissionCatalog`. When adding a permission in PHP, add `name` + `description` to both `locales/vi/permissions.json` and `locales/en/permissions.json` in the same change.

### Audit action / subject labels

- Store API action codes as English dotted strings (`settings.updated`). Display via nested keys: `audit:actions.settings.updated` (helper: `resources/js/lib/i18n/audit-labels.ts`).
- Subject morph / FQCN is stripped to the model basename and mapped under `audit:subjects.*` (e.g. `Company` → “Công ty”).
- When adding a new `AuditLogger::write(action: '…')` call, add the matching `actions.*` entry in both locales **and** append the code to `AUDIT_ACTION_CODES` in `audit-labels.ts` (powers the audit filter select).
- System role keys (`admin`, `hr`, `manager`, `employee`) display via `roles:system_roles.*`; custom roles keep the API `name`.
- Audit filter UI uses localized selects: action codes and subject morph FQCNs are sent to the API; users only see translated labels.
- Onboarding task titles: localize by stable `task.key` via `onboarding:tasks.*` (helper `onboarding-labels.ts`); API `title` remains the fallback for custom tasks.
- Report table columns: localize API row keys via `reports:columns.*` (helper `report-labels.ts`); status cells reuse `common` / `leave` / `payroll` status maps by **applied** report type; leave types via `leave_type_code` + `leave:leave_types.*` (helper `leave-labels.ts`); dates locale-formatted.
- Leave type names: localize by stable `code` via `leave:leave_types.*` (helper `leave-labels.ts`); API `name` remains fallback for custom types. Used on leave request form, balances, request list, and leave reports.
- Notification inbox copy: localize by stable `type` via `notifications:messages.*` (helper `notification-labels.ts`). Backend writes use `lang/{vi,en}/notifications.php` resolved to the recipient locale.
- Shift kind enums: localize via `shifts:kind.*` (helper `shift-labels.ts`); keep API codes (`standard`, `night`, …) unchanged.

## Hard rules (agents & humans)

1. **No new user-facing hardcoded English or Vietnamese strings** in `pages/`, `features/`, or shell components — use translation keys.
2. When shipping a new module screen, add keys to **both** `locales/vi/` and `locales/en/` in the same PR.
3. Prefer stable key names (`employees.list.title`), not English sentences as keys.
4. Dates and numbers: use locale-aware formatters (`Intl` with effective locale), not hardcoded `en-US` / `vi-VN` unless justified.
5. Domain status enums in APIs stay English codes (`active`, `approved`); display labels go through i18n.
6. Do not use Inertia shared props as the locale source of truth for HRM SPA screens.

## Language switcher

- Place in app header and/or user menu ([LAYOUT.md](./LAYOUT.md)).
- Authenticated: `PUT /api/me/locale` with `{ "locale": "vi" | "en" | null }`, then `i18n.changeLanguage` + refresh auth payload.
- Company default: editable on Company settings as a `select` (`vi` / `en`), not free text.

---

## Adding keys for a new module

1. Create or extend `resources/js/locales/vi/{module}.json` and `en/{module}.json`.
2. Register the namespace in `lib/i18n` if required by the init config.
3. Use `useTranslation('{module}')` in pages/features.
4. Keep API error `message` displayable; SPA shows `DomainException` / validation messages from the API (already localized via Laravel `lang/{vi,en}` when locale is set).

---

## Backend locale

Laravel `app()->setLocale()` is set by middleware from the same resolution order.

User-facing `DomainException` messages **must** use `__('…')` with catalogs under:

```
lang/vi/
lang/en/
```

Keep stable `error_code` values in English snake/UPPER style; translate only the human `message`. Do not invent a parallel client-only validation namespace until needed.
